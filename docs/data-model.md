# Модель данных

Владелец — напарник. Логическая схема для PostgreSQL и Prisma, этап 2a. Основа — [PRD](PRD.md), [принятые решения](context.md) и [условие хакатона](hackathon-task.md).

Основные сущности имеют UUID. Таблицы связей могут использовать составной ключ из UUID. Моменты времени храним как `timestamptz`. Границы учебного дня, недели и календарные напоминания считаем в `Europe/Moscow`. Персональные данные в сидах и расписании вымышленные.

## Вход, профиль и принадлежность

| Сущность | Основные поля и связи | Ограничения |
| --- | --- | --- |
| `User` | `login`, `passwordHash`, `role` (`student`, `staff`), `disabledAt` | Уникальный нормализованный логин. Пароль хранится только как хэш argon2id. |
| `Session` | `userId → User`, `tokenHash`, `expiresAt`, `revokedAt` | Уникальный хэш случайного токена. В cookie только исходный токен, с атрибутами `HttpOnly`, `Secure`, `SameSite=Lax`. Выход отзывает сессию. |
| `StudentProfile` | Уникальный `userId → User`, `groupId → Group`, ФИО, направление, форма обучения, номер студенческого | Один профиль на студента. Институт и курс берём из группы. Контакт для уведомлений хранится отдельно. |
| `Institute`, `Group` | Справочник институтов. У группы `instituteId`, уникальный код и курс | Публикация для курса задаётся вместе с институтом. |
| `GroupHead` | `groupId → Group`, `studentId → StudentProfile` | Один староста на группу, только из этой группы. Сервер проверяет актуальное членство. |
| `StaffInstitute` | `userId → User`, `instituteId → Institute` | Уникальная пара. Назначения задаются сервером. В демо сотруднику явно назначаются три нужных института. |
| `UserPreferences` | Уникальный `userId`, тема, адрес и состояние e-mail-уведомлений | Контакт доступен владельцу и серверу доставки. Переключатели каналов по типу добавляются с N4. |

Сервер разрешает сессию и проверяет срок, отзыв и активность аккаунта. Из этого контекста берёт `userId`, актуальную роль и область доступа. Лимит попыток входа проверяется до argon2id. Для лимита используем серверное хранилище с временем истечения и атомарным счётчиком.

## Расписание и учебные результаты

| Сущность | Основные поля и связи |
| --- | --- |
| `AcademicTerm`, `AcademicWeek` | Семестр с датами начала и конца. Номер учебной недели уникален внутри семестра, дата её начала хранится отдельно от номера ISO. |
| `Subject`, `Teacher`, `Campus`, `Room` | Дисциплина, преподаватель с вымышленным ФИО, корпус с адресом и ссылкой на карту, аудитория с номером и этажом. Номер аудитории уникален внутри корпуса. |
| `Lesson` | Одно занятие для одной группы. `groupId`, `subjectId`, `termId`, тип, подгруппа при наличии, необязательная аудитория, преподаватели через `LessonTeacher`. Текущие `startsAt`, `endsAt`, формат, онлайн-ссылка, `status` и `version`. Время окончания позже начала. |
| `LessonChange` | `lessonId`, `version`, тип изменения, автор и его роль на момент публикации, `publishedAt`, `previousStartsAt` и `newStartsAt`, снимки остальных полей «было → стало» (окончание, формат, аудитория, ссылка, статус). Уникальная пара `(lessonId, version)`. |
| `Assessment`, `AssessmentResult` | Оценочное событие с `groupId`, `subjectId`, `termId`, видом работы и датой. Результат относится к студенту и событию, имеет `publishedAt`, значение и обозначение шкалы либо результат зачёта. Уникальная пара `(studentId, assessmentId)`. |
| `StudentTermStanding`, `AdmissionItem` | Статус допуска к сессии на студента и семестр. Для G3 — пункт чек-листа на студента, дисциплину и семестр с дедлайном, прогрессом и статусом. |

Версию пары обновляем с проверкой ожидаемой версии. В одной транзакции меняем текущее состояние, добавляем историю и создаём уведомление. При конфликте сотрудник перечитывает пару перед повторной правкой. Перенос между днями отображается в «Сегодня» по исходной и новой дате. Отменённую пару исключаем из поиска ближайшей, а её изменение сохраняем в ленте. Массовая публикация сначала проверяет доступ ко всем выбранным парам.

Для R5 загружаем развернутые занятия из очищенного набора. До проверки российского VPS и условий использования источника демо работает на вымышленном расписании. Исходные ФИО, коды групп и сырые календари в БД приложения не попадают. Явные переносы для R3 создаются в кабинете. См. [исследование расписания](research/schedule-source.md).

Правила среднего балла, долгов и допуска уточняются по открытым вопросам PRD. История хранит шкалу результата, чтобы сводка не смешивала несовместимые оценки. Состав и происхождение документов помощника также остаются открытыми.

## Дедлайны, объявления и заявки

| Сущность | Основные поля и связи |
| --- | --- |
| `Deadline`, `Announcement` | Автор и его роль на момент публикации, заголовок, текст, время публикации. У дедлайна есть `dueAt`, дисциплина при наличии и версия срока. |
| `DeadlineGroup`, `AnnouncementGroup` | Связи публикаций с группами. Перед записью сервер разворачивает выбранную аудиторию в список разрешённых групп и сохраняет его. |
| `DeadlineProgress` | Уникальная пара `(deadlineId, studentId)` и `completedAt` для D3. |
| `ApplicationType` | Код и название позиции каталога, список полей формы и допустимые способы получения. |
| `Application` | `studentId`, `typeId`, `submissionGroupId` на момент подачи, проверенные поля формы, минимальный снимок профиля для заявки, способ получения, текущий статус, время подачи и номер версии. Повторная подача создаёт новую заявку и может ссылаться на предыдущую свою. |
| `ApplicationStatusEvent` | `applicationId`, версия, старый и новый статус, автор, время, причина отказа. Уникальная пара `(applicationId, version)`. |
| `PickupSlot`, `PickupReservation` | Интервал и место выдачи, институт, действующая бронь слота и заявка (A3). Один слот занимает одна заявка. В истории заявки сохраняются время и место после освобождения брони. |

Статусы A4 идут по цепочке «Подана → В работе → Готова → Выдана», с веткой «Отклонена» и обязательной причиной. В транзакции проверяем ожидаемую версию и право сотрудника, обновляем заявку, пишем событие и создаём уведомление владельцу. При записи брони проверяем доступность и пересечение с действующим расписанием студента. Если слот занят, студент получает предложение выбрать другой. Черновик AI2 попадает в этот поток после подтверждения студентом.

## Лента, доставка и помощник

| Сущность | Основные поля и связи |
| --- | --- |
| `Notification` | Тип, важность, время, типизированная ссылка на `LessonChange`, `Deadline`, `Announcement` или `ApplicationStatusEvent`. Уникальный ключ события исключает повторное создание. |
| `NotificationRecipient` | `notificationId`, `userId`, `readAt`. Уникальная пара `(notificationId, userId)`. Строки создаются из разрешённой аудитории при публикации. |
| `NotificationDelivery` | Получатель, канал (`webPush`, `messenger`, `email`), идентификатор назначения, состояние, число попыток, `nextAttemptAt`, `leaseExpiresAt`, `sentAt` и код последней ошибки. Уникален ключ «получатель + канал + назначение». |
| `DeadlineReminder` | Дедлайн, версия срока, смещение (`3d` или `1d`), `scheduledAt`, состояние. Уникальный ключ `(deadlineId, dueVersion, offset)`. При переносе старые задания отменяются. |
| `MessengerBinding` | `userId`, провайдер (`max` или `vk`), зашифрованный идентификатор диалога, время привязки и отзыва. Одна действующая привязка на пользователя и провайдера. Уникальный серверный отпечаток диалога на провайдера. |
| `MessengerLinkCode` | `userId`, провайдер, хэш одноразового кода, срок 10 минут, время использования. Привязка создаётся в транзакции с погашением кода. |
| `PushSubscription` | `userId`, endpoint и ключи подписки, время создания и отзыва. Уникальный отпечаток endpoint. |
| `HelpDocument`, `HelpDocumentSection` | Заголовок, источник, версия, признак публикации, номер и текст пункта. Номер пункта уникален в версии документа. |

Фиксируем событие, получателей и задания на доставку в той же транзакции, что и изменение. Воркер забирает задания атомарно, повторяет временные сбои после окончания захвата и перед отправкой проверяет актуальность аудитории, подписки и настроек. Планировщик создаёт отдельное событие на каждое напоминание, используя ключ `DeadlineReminder`. Перед отправкой проверяем версию срока и отметку «сделано». Ключ доставки предотвращает повторное создание задания. Если провайдер принял сообщение, а ответ потерялся, повторная отправка может дать дубль при отсутствии идемпотентности у провайдера. Для S2 измеряем время от публикации до отправки, а получение push и сообщения за 60 секунд проверяем на тестовом устройстве.

Привязки и подписки доступны серверу доставки. В профиль отдаём только состояние подключения и действия для включения или отвязки. Токены провайдеров и ключи сервера берём из серверного окружения. Помощник использует опубликованные пункты и только данные пользователя из текущей сессии. Лимит AI3 — 20 запросов в час на пользователя, проверяется на сервере до вызова провайдера.

## Доступ и данные в ответах

| Данные | Студент | Староста | Сотрудник |
| --- | --- | --- | --- |
| Профиль, оценки, настройки, собственные заявки и их история | Свои | Свои | Только необходимые поля заявки и её история в назначенных институтах. Оценки и настройки студентов недоступны. |
| Расписание, дедлайны, объявления | Для своей группы | Для своей группы. Публикует только туда. | Для групп назначенных институтов. Публикует для групп, курса или института в пределах назначений. |
| Уведомления | Свои, с доступной ссылкой на объект | Свои. Для своей публикации доступно только число прочтений и размер аудитории. | Действия в пределах назначений. Личные подписки и отметки студентов недоступны. |
| Помощник | Опубликованные пункты и свои данные | То же | Студенческий чат недоступен. |

Списки и запросы по ID сразу ограничиваются владельцем, группой или назначенным институтом. Сервер возвращает 404 на чужой объект и отказывает студенту в доступе к `/staff`. После проверки сериализует только поля из явного списка для роли. UUID, группы и роль из запроса не определяют область доступа. На фронтенд не отдаются хэши, ключи, идентификаторы диалогов и сырые записи доставок.

## Запросы и индексы

| Запрос | Индекс или ключ |
| --- | --- |
| Ближайшая пара и расписание на день/неделю | `Lesson(groupId, startsAt)` для действующих пар. В начале запроса определяется группа из профиля. |
| Изменения с исходной или новой датой сегодня и завтра | `LessonChange(previousStartsAt, lessonId)` и `LessonChange(newStartsAt, lessonId)`. Фильтр по группе выполняется через `Lesson`, совпавшие по обеим датам записи объединяются по ID. |
| Дедлайны на 7 дней | `DeadlineGroup(groupId, deadlineId)` и `Deadline(dueAt, id)`. Отметка о выполнении берётся по ключу `(deadlineId, studentId)`. |
| Новые оценки и активные заявки | `AssessmentResult(studentId, publishedAt DESC)` и `Application(studentId, status, submittedAt DESC)`. Активные статусы — «Подана», «В работе», «Готова». |
| Очередь дирекции | `Group(instituteId, course)` и `Application(submissionGroupId, status, submittedAt DESC)`. |
| Лента, непрочитанное, фоновые задания | `NotificationRecipient(userId, readAt)`, `Notification(publishedAt DESC, id)`, `NotificationDelivery(status, nextAttemptAt)`, `DeadlineReminder(status, scheduledAt)`. |

На «Сегодня» сервер независимо выбирает ближайшую пару, изменения, дедлайны, новые оценки и активные заявки в порядке T1. После появления сидов проверяем планы запросов `EXPLAIN` на демо-данных и проверяем границы дат в МСК.

## Проверки для реализации

1. S1/S2. Перенос пары между днями даёт корректное «было → стало», новую ближайшую пару и уведомление только нужной группе. Повтор публикации или конфликт версии не создаёт вторую запись.
2. S3/S8. Перенос дедлайна отменяет старые задания. Привязка погашает код один раз, просроченный код отклоняется, отвязанный канал не получает новое сообщение.
3. S4. Подача автозаполняет разрешённые поля. Каждая смена статуса попадает в историю и уведомление. Два параллельных запроса на один слот дают одну бронь.
4. S6/S9. Студент получает 404 на чужую заявку и профиль. Староста не может опубликовать в чужую группу, сотрудник — обработать заявку из неназначенного института. Счётчик старосты не раскрывает личности.
5. NF6. В сидах и результатах импорта только вымышленные персональные данные. Повторный сброс восстанавливает демо и не оставляет в очереди заданий из удалённых демо-событий.
