## Общая оценка

Сильная основа прототипа для хакатона. Есть сквозные сценарии студента и сотрудника, серверная авторизация, база с миграцией, собственный визуальный стиль, вымышленные данные и подробная история решений. Идея своевременных уведомлений связана с результатами опроса.

Готовность к финальному показу пока требует проверки доставки и устранения рисков ниже. Большое количество документов само по себе не подтверждает работу сценариев на опубликованном сайте.

## Найденные проблемы

### P1 — произвольный адрес push позволяет инициировать запросы с сервера

`src/app/(cabinet)/profile/push-actions.ts`, функция `valid`, проверяет только начало `https://` и длины строк. Сервер сохраняет адрес, а `src/server/push.ts` передаёт его в `webpush.sendNotification`. Пользователь может зарегистрировать собственные корректные ключи и внутренний HTTPS-адрес вместо адреса push-провайдера. Для отправки необходимы настроенные VAPID и событие, предназначенное этому пользователю.

Локальная проверка без сетевого запроса подтвердила, что установленная библиотека принимает `https://127.0.0.1:9443/internal` в `generateRequestDetails` с корректными синтетическими ключами. Это подтверждает отсутствие защиты в библиотеке на этапе подготовки запроса; эксплуатация на VPS не проводилась.

Рекомендация — разрешать только проверенные адреса поддерживаемых push-провайдеров, валидировать URL и ключи, исключить внутренние адреса. Если разрешение строится на DNS, учитывать повторное разрешение адреса и перенаправления. Ограничить частоту и количество регистраций подписок.

### P1 — зависшая отправка push останавливает обработку очереди в процессе

`src/server/push.ts` не передаёт `timeout`. Установленная библиотека включает его только при явной настройке. В `src/server/delivery.ts` обработчик держит `running = true` до завершения всего `Promise.allSettled`. Пока один запрос не завершился, следующие проходы этого процесса возвращаются сразу. Продление аренды само по себе это не исправляет. При нескольких процессах истёкшее задание может быть отправлено повторно.

Рекомендация — задать сетевой тайм-аут и общий предел длительности попытки, меньшие аренды 60 секунд, затем проверить восстановление после зависания и отказа провайдера.

### P2 — скорость очереди недостаточна для цели доставки за минуту

`processDeliveries(limit = 10)` забирает один пакет, периодический вызов выполняется раз в 15 секунд (`src/instrumentation.ts`). Один перенос с 80 заданиями при отсутствии других публикаций потребует восьми проходов; последний начнётся примерно через 90–105 секунд даже при быстрых ответах провайдера. Это расчёт по коду, нагрузочный замер не выполнялся. Два канала дополнительно увеличивают число заданий.

Рекомендация — обрабатывать следующие пакеты сразу после завершения предыдущего с ограничением параллелизма и времени работы. Проверить группу с двумя каналами и измерить получение писем во входящих отдельно от принятия SMTP-сервером.

### P2 — при переносе между днями теряется понятное «было → стало»

`src/server/queries/schedule.ts` выбирает пары только по новому `startsAt`, поэтому в исходном дне строка перенесённой пары исчезает. В новой дате статус содержит лишь прежнее время (`mskTime`), а `src/components/board/status.tsx` показывает «перенос · было 09:00». При переносе на другой день на то же время получается новое 09:00 и прежнее 09:00 без указания исходной даты. В ветке PR №48 точка изменений отмечает обе даты, но сама по себе не объясняет перенос. Когда пара начинается, статус «идёт» также заменяет метку изменения.

Рекомендация — сохранить ссылку на перенос в исходном дне, показывать обе даты и времена, а состояние «идёт/прошла» отображать отдельно от истории изменений. Добавить проверку переноса на другой день с сохранением времени.

Для VPS добавить проверку готовности, резервное копирование и проверенное восстановление. Утренний `db:seed` полностью пересоздаёт демо-базу, это нужно явно учитывать при показе сохранённых заявок.
6. После обязательных исправлений выбрать одну дополнительную функцию. Роль старосты H1 логично продолжает основную идею. Помощник AI1/AI2 потребует реализации серверного клиента, лимитов и проверок ответов; наличие подготовленных документов и переменных окружения не означает готовность чата. Поиск и PDF-справку оставить после стабильного ядра. Пересобрать итоговый отчёт с актуальными скриншотами и подтверждёнными результатами.
